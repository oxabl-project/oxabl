## Project Overview

Oxabl is a high-performance tooling suite for Progress ABL (Advanced Business Language), written in Rust. The project aims to provide blazingly fast developer tools for ABL code (formatting, linting, parsing, etc.). This is an unofficial project with no affiliation with Progress Software.

## Build Commands

```bash
# Build the entire workspace
cargo build

# Build a specific crate
cargo build -p oxabl_lexer

# Run tests for the entire workspace
cargo test

# Run tests for a specific crate
cargo test -p oxabl_lexer

# Run a single test
cargo test -p oxabl_lexer -- test_name

# Check code without building
cargo check
```

## Code Generation

The lexer uses generated code for ABL keywords, operators, and the keyword matching function. The `oxabl_codegen` crate parses reference HTML/JSON files from `resources/` and generates Rust code.

```bash
# Write all generated files (default)
cargo run -p oxabl_codegen

# Write specific file(s)
cargo run -p oxabl_codegen -- kind     # Writes kind.rs (enum + match function)
cargo run -p oxabl_codegen -- atoms    # Writes build.rs (complete file)
cargo run -p oxabl_codegen -- callable # Writes callable.rs (is_callable_kind)
cargo run -p oxabl_codegen -- builtins # Writes builtins.rs (built-in function registry)
cargo run -p oxabl_codegen -- grammar  # Writes the VS Code extension's TextMate grammar
cargo run -p oxabl_codegen -- keyword-docs # Writes keyword_docs.rs (hover's statement and function docs)
cargo run -p oxabl_codegen -- snippets # Writes completion/snippets.rs (the server's snippets, from clients/vscode/snippets/abl.json)

# Show statistics without writing files
cargo run -p oxabl_codegen -- summary
```

Generated files are written directly to their target locations and include a "DO NOT EDIT" header. The CI job `Grammar drift` also regenerates `crates/oxabl_pipeline/src/keyword_docs.rs` and `crates/oxabl_pipeline/src/completion/snippets.rs` and fails when a committed file is not the generated one. A change of `clients/vscode/snippets/abl.json` therefore needs `cargo run -p oxabl_codegen -- snippets` in the same change.

### The VS Code grammar

`clients/vscode/syntaxes/abl.tmLanguage.json` is generated. Change its structure in `resources/abl.tmLanguage.template.json` (`{{word:NAME}}`, `{{keywords:CATEGORY}}`, `{{boundary}}` and `{{non-boundary}}` placeholders, and `x-nesting-limit` on a rule that includes itself) or the keyword data, then run `cargo run -p oxabl_codegen -- grammar`. The CI job `Grammar drift` fails when the committed grammar is not the generated one. Test it from `clients/vscode`: `pnpm test` (corpus and regex compile), `pnpm run test:grammar` (assertion and snapshot tests), `OXABL_E2E_OXABL=$PWD/../../target/debug/oxabl OXABL_E2E_RUNTIME=<short dir> xvfb-run -a pnpm run test:e2e` (the packaged VSIX in a real VS Code; run `cargo build -p oxabl` first, because the `outline`, `definition`, `folding`, `references` and `reference-lenses` scenarios use the real language server and fail without these variables). The categories, the rules and the release and self-update design are in `docs/design/vscode-extension.md`.

The extension's snippets are in `clients/vscode/snippets/abl.json`, with each keyword in a `<<...>>` marker so the extension can write it in the project's keyword case. `crates/oxabl/tests/vscode_snippets.rs` parses every body with oxabl in both cases, and fails on a keyword outside a marker, and `pnpm test` checks the markers. `clients/vscode/test/keyword-case.json` is a table of `oxabl.toml` texts with the keyword case the server uses; vitest checks the extension's reader (`keywordCaseOf`) against it and `vscode_snippets.rs` checks `WorkspaceConfig` against it, so add a text there when you change the reader. Keep a keyword outside a marker out of a body.

### The OpenEdge metaschema catalog

`crates/oxabl_schema/resources/metaschema.df` is a generated `.df` describing
the dictionary and virtual system tables that every OpenEdge database carries
(`_file`, `_field`, `_index`, `_connect`, ...). A `.df` dump never contains
them, so no project can supply them. It is parsed once per process and
*borrowed* by every loaded schema — never copied — and the user's own tables
always win a name collision.

It is generated by shell rather than `oxabl_codegen`, because it can only be
produced from a licensed OpenEdge installation:

```bash
DLC=/path/to/dlc scripts/gen-metaschema-df.sh
```

See `crates/oxabl_schema/METASCHEMA.md`.

Run it with `TMPDIR` set to a short directory, as the other LSP tests.
- `crates/oxabl/tests/semantic_tokens_lsp.rs` tests the semantic tokens through `oxabl lsp`: each kind of name, the names with no token, delta, range, the setting and a stale request (`docs/design/semantic-tokens.md`). A source with `OXABL-TEST-HOLD:lsp.semantic-tokens`, `OXABL-TEST-HOLD:lsp.semantic-snapshot` or `OXABL-TEST-HOLD:lsp.semantic-answer` makes the request wait before its analysis, while the analysis holds its database snapshot, or after it, in test builds only.
- `crates/oxabl/tests/hierarchy_lsp.rs` tests go to implementation, go to super method and the type hierarchy through `oxabl lsp` (`docs/design/type-hierarchy.md`). A class file with `OXABL-TEST-HOLD:daemon.hierarchy-index@<ms>` makes the reverse index wait while it reads that file, in test builds only, so a test can cancel a request in the middle of the index.
- `crates/oxabl/tests/completion_*_lsp.rs` test code completion through `oxabl lsp` (the engine is `oxabl_pipeline::completion`, the bases and the refresh are `oxabl_daemon::completion`, the requests and rendering are `oxabl_lsp::completion`; `docs/design/completion.md`). A source with `OXABL-TEST-HOLD:completion.refresh` makes the background refresh of a stale base wait before its analysis, in test builds only, so a test shows that a request and an edit never wait for it.
- `crates/oxabl/tests/schema_cache.rs` tests the schema cache through `oxabl check`: the second run parses no `.df` file, a change of one byte, a new build (also one with the size and the time of this build), a damaged entry (also one with the size and the structure intact, which the hash of the entry refuses), a FIFO at the path of an entry, a mode other than `developer`, the removal of old entries, the use of an entry as its age, and that a test build never writes to the home of the user. `crates/oxabl/tests/schema_cache_lsp.rs` tests that `oxabl lsp` writes and reads the entry. A test build uses the cache only with `OXABL_SCHEMA_CACHE_DIR` set, and `Launch::schema_cache` of `tests/lsp/session.rs` sets it for a session. A test build of the binary counts the schema files it parses (`oxabl_common::schema_file_parsed`) and prints the count when `OXABL_TEST_SCHEMA_PARSES` is set. `crates/oxabl_schema/tests/cache.rs` tests `SchemaLoader::load_files_cached` and the binary form with a cache in memory. Run both with `TMPDIR` set to a short directory.
- `crates/oxabl/tests/daemon_start_lsp.rs` tests the start of the daemon through `oxabl lsp`: a slow start still serves and is shown to the editor, a daemon that exits during the start is reported at once, a daemon that never serves ends the wait at the limit, and a daemon that a restart started still serves other clients after the client that started it has exited and the read end of its stderr is closed, and the last line of a daemon that aborts reaches the editor (`docs/overview.md`, the `oxabl daemon` entry). A workspace root whose path holds `OXABL-TEST-HOLD:daemon.ready@<ms>` makes the daemon wait just before it registers, `OXABL-TEST-PANIC:daemon.ready` makes it exit there, a buffer with `OXABL-TEST-ABORT:lsp.diagnostics` makes it write 512 KiB and a line to stderr and abort (`oxabl_common::abort_if_injected`), and `OXABL-TEST-LIMIT@<ms>` shortens the 60 s limit of the wait (`oxabl_common::injected_limit`), in test builds only.
- `crates/oxabl/tests/daemon_exit_lsp.rs` tests when the daemon of `oxabl lsp` exits: its root removed, moved or replaced (a replaced root ends only a daemon with no client), the idle timeout (`OXABL_DAEMON_IDLE_TIMEOUT`, set short in the test), no exit while a client is connected, an idle exit after the runtime directory was removed, a new daemon for the next client, and a test that panics. The `Session` helper stops the daemon by pid when it drops (also on a panic) and signals a pid only when it is the `oxabl daemon` of the build under test, and gives a test daemon the idle timeout `2m` as a backstop; a test that leaves its daemon alone must set its own timeout or stop it. The root check (a descriptor of the root, opened at the start, and a thread of its own) and the accept loop are in `oxabl_daemon::root_watch` and `oxabl_daemon::listener` (`crates/oxabl_daemon/tests/idle_exit.rs` tests them without a process).
- `scripts/soak/` drives `oxabl lsp` and `oxabl daemon` and counts memory, threads and processes; see `scripts/soak/README.md`.
- `clients/vscode/test/grammar/fuzz.test.ts` fuzzes the TextMate grammar for slow lines and deep rule stacks (`pnpm test`; a longer run with `OXABL_FUZZ_SECONDS`).

## Architecture

### Workspace Structure

- `crates/oxabl` - Umbrella library (the curated public API) and the CLI binary. `oxabl skill show|install` (`src/skill.rs`) embeds the agent skill from `crates/oxabl/skill/` (`SKILL.md` plus `references/*.md`, version `dev` in the source) through the fixed `FILES` list; add a skill file to that list as well as to the directory, or `skill_cli` fails. `skill_drift` checks every `oxabl` line in a `sh` block and every inline code span that starts with `oxabl ` against the binary's `--help` (and runs each `oxabl skill show <file>` example), so write every shell example in a `sh` fence (output in `text`); a fence tag outside `sh`, `text`, `toml`, `json` and `ini` fails it. `skill_toml` loads every `toml` block as an `oxabl.toml`, and `skill_rules` compares `references/rules.md` with the rule registry and the diagnostic codes of the sources. `oxabl skill install` is user-level only: it keeps one store, `${XDG_DATA_HOME:-~/.local/share}/oxabl/skills/oxabl/` (the data directory of `src/paths.rs`, shared with the self-update install record), replaces it as a whole through a sibling staging directory, and links `~/.agents/skills/oxabl` and `~/.claude/skills/oxabl` to it. A link that is not a symlink to the store is foreign and refused (exit 2, nothing written, preflight first); `--force` renames it to `${XDG_DATA_HOME:-~/.local/share}/oxabl/skill-backups/<agents|claude|store>-<UTC timestamp>`, outside the skills folders because agents scan those and would load a backup as a second skill; the moves run before any other write, a failed rename (another filesystem) exits 2 naming the entry with nothing else written, and an entry is never copied and deleted. Where a symlink is not possible it copies the store there, and such a copy counts as oxabl's. There is no manifest. `skill_cli` runs every install with its own `HOME` and `XDG_DATA_HOME`; never run `oxabl skill install` against the real home in a test or a manual check. Its `self-update` cargo feature (off by default, like `remote-cache`; the release binary has both) adds `oxabl self-update` and the background check of a managed binary (`src/self_update/`: the GitHub reader, the install procedure, the install record, the schedule). It reuses the `reqwest` and `rustls` stack that `remote-cache` links, so no second HTTP stack. `scripts/install.sh` is the installer and shares the install record (`install.json`) with the updater and the VS Code extension
- `crates/oxabl_pipeline` - The shared lint and format run every client drives, the document outline (`outline`, and `outline_with_includes` for the declarations of include files; see `docs/design/document-outline.md`), folding and selection ranges (`syntax`, see `docs/design/folding-selection.md`), go to definition, hover and document links (`navigation`, see `docs/design/navigation.md`), semantic tokens (`navigate/semantic.rs`, see `docs/design/semantic-tokens.md`), signature help and the parameter-name inlay hints (`navigate/signature.rs`, with the syntax of the built-in functions in `builtin_signatures.rs`, see `docs/design/signature-help.md`), find references and the call hierarchy in one compilation unit (`references`, see `docs/design/references.md`), the class or method at the cursor for go to implementation, go to super method and the type hierarchy (`hierarchy`, see `docs/design/type-hierarchy.md`), the database inlay hints (`hints`, see `docs/design/inlay-hints.md`), format a selection (`format_range`, see `docs/design/range-formatting.md`), the schema text of a table or field (`schema_hover`), the schema browser's tree of the configured `.df` files (`schema_view`, see `docs/design/schema-browser.md`), and the code completion engine (`completion`: the context finder, the collectors, keyword case, ranking; it reads a base that the daemon keeps, see `docs/design/completion.md`); sits *beneath* `oxabl_lsp`, `oxabl_wasm`, and the umbrella
- `crates/oxabl_index` - Cross-file fact extraction, the in-run batch index, the static call graph and the inheritance graph (`hierarchy`: the supertypes a class header names, resolved with what did not resolve kept, the reverse index of subtypes, and the methods that override or implement another; see `docs/design/type-hierarchy.md`). The producer scan asks of each file with a `{` whether `index_file` may expand it; `expansion_scan` says yes from the tokens for a class or interface header and parses every other file, because an include, a reference or a directive can mend a text that does not parse as written (the `END.` of a block the file opens, a block header that an `&IF` picks). `crates/oxabl/tests/check_producer_prefilter.rs` counts the parses per root of a test build. Sits *beneath* `oxabl_pipeline`
- `crates/oxabl_daemon` - The session core: one salsa instance per workspace root, serving several clients; the **only** crate that may know about salsa. Its `completion` module keeps the newest analysis (base) of each open document for code completion and refreshes a stale one in the background, so a completion request on a stale base never waits for an analysis (the first request on a document makes its base on the request thread) (`OXABL-TEST-HOLD:completion.refresh` holds the refresh in test builds). Its `references` module takes a references or call hierarchy search over the other files of the workspace, through the dependency graph; its `hierarchy` module answers go to implementation, go to super method and the type hierarchy from the reverse inheritance index (`oxabl_index::hierarchy`), built per request from the memoized facts of each class file (`docs/design/type-hierarchy.md`)

### Lexer (`oxabl_lexer`)

The lexer should classify tokens as distinctly as possible so the parser dispatches on `Kind` enum variants (O(1) integer comparison), never on runtime string comparison or `to_uppercase()` allocations. When a new keyword is needed by the parser, add it to `keyword_overrides.toml` and regenerate — do not use `eq_ignore_ascii_case()` workarounds.

**Avoid heap allocations on hot paths.** ABL keywords are ASCII-only, so case-insensitive matching uses a `[u8; 64]` stack buffer with `to_ascii_lowercase()` byte folding — never `s.to_lowercase()` which heap-allocates a `String`. Eliminating the `to_lowercase()` allocation in `match_keyword()` (called on every token) yielded a ~20% overall performance improvement. The codegen emits a compile-time assertion that the longest keyword fits in the buffer. The same principle applies anywhere in the lexer: prefer `eq_ignore_ascii_case()` (zero-allocation byte comparison) over `to_lowercase()` + match.

The lexer tokenizes ABL source code into a stream of tokens. Key components:

- **Token**: Contains `kind` (token type), `start`/`end` byte offsets, and `value` (for literals)
- **Kind**: Enum of all token types (operators, keywords, identifiers, literals)
- **TokenValue**: Enum for literal values (Integer, BigInt, Decimal, String, Boolean, None)

The lexer uses `string_cache` for interned strings (atoms). Atoms are generated at build time via `build.rs` which includes all ABL keywords.

ABL-specific features handled:
- Case-insensitive keywords with abbreviations (e.g., `def`, `defi`, `define` all map to `Kind::Define`)
- Tilde (`~`) as escape character in strings
- Date constants: digit runs joined by `/` with no whitespace (`02/01/2026`, `2/1/26`, `10/2`) are one `Kind::DateLiteral` token, as the compiler reads them. `10 / 2` is a division. The token keeps its spelling, because the order of the parts follows the `-d` startup parameter
- Hyphens allowed in identifiers (`my-variable-name`)
- Preprocessor directives (`&if`, `&scoped-define`) and references (`{&variable}`)
- Include file references (`{file.i}`, `{file.i args}`, `{file.i &name=value}`)
- Include positional argument references (`{0}`, `{1}`, `{2}`)
- Line (`//`) and block (`/* */`) comments

### Code Generation (`oxabl_codegen`)

Parses ABL keyword reference data from:
- `resources/abl_keyword_index.html` - Keyword list with reserved status and abbreviations
- `resources/abl_keyword_index.json` - Keyword types and documentation URLs
- `resources/keyword_overrides.toml` - Manual additions, overrides, and removals

Generates:
- `Kind` enum with categorized token types
- Atom list for `string_cache_codegen`
- `match_keyword()` function handling abbreviations and case-insensitive matching

## CI & Release Process

Every job in `ci.yml` and `codspeed.yml` has a `timeout-minutes` of about three times its usual run time, so a hung step (such as a toolchain setup that never returns) fails in minutes, not after GitHub's six-hour default. Raise a job's limit when it grows; do not remove it.

Every workflow sets up Rust with the local action `.github/actions/setup-rust`: the runner's own `rustup` installs the toolchain, `actions/cache` restores the cargo registry, and `cargo install --locked` builds the cargo binaries a job needs, each pinned as `name@version` and cached after the first build. Each network call in it has its own time limit, since a composite step takes no `timeout-minutes`. It calls no GitHub API and uses no third-party action; `moonrepo/setup-rust`, which it replaced, hung for the whole job timeout when `cargo-binstall` met GitHub's API rate limit. The action saves caches on `master` only, which every branch and pull request can read; a pull request only restores. Only the `Check` job saves the registry (`save-registry: true`), after `cargo fetch` of the workspace and the fuzz crate, so the entry holds every dependency; every other job only restores it. Raise a pinned binary's version in the workflow that names it. Target directories are not cached: one is several GB, and a set of them passes the repository's cache limit and evicts itself. The `Check` job fails when a workflow or local action uses an action outside its allowlist (first-party `actions/*`, local actions, and the few it names): add an action there only on purpose.

### Automated Releases (`.github/workflows/release.yml`)

Uses [Release Please](https://github.com/googleapis/release-please) for fully automated versioning and changelogs. Use conventional commits.

**Config files:**

- `release-please-config.json` — release type and which `Cargo.toml` files to update
- `.release-please-manifest.json` — tracks the current version

While pre-1.0, `bump-minor-pre-major` is enabled so breaking changes bump minor instead of major.

The VS Code extension (`clients/vscode`) is its own Release Please component, `oxabl_vscode` (`release-type: node`, tags `oxabl_vscode-vX.Y.Z`). The `vsix` job packages it with `clients/vscode/scripts/package-vsix.sh` (the script the CI job `VS Code client` runs on every pull request) and uploads `oxabl-vscode-<version>.vsix` and its `.sha256` to that release. The extension updates itself from those two assets, so their names are a contract (`docs/design/vscode-extension.md`).

The release workflow's `binary` job builds the static Linux binary with `--features remote-cache,self-update` (`scripts/build-musl.sh`, in a `rust:alpine` container) and uploads it with a `.sha256` file to the release of the `oxabl` crate. On `workflow_dispatch` it runs only with the input `tag` naming an existing `oxabl-vX.Y.Z` release, and builds that tag (the `vsix` job likewise with an `oxabl_vscode-vX.Y.Z` tag): the way to add the assets to a release whose asset jobs did not run. Without `tag`, a manual run uploads nothing. The CI job `musl-binary` builds the same binary on every pull request and starts it in `ubuntu:22.04` (`scripts/check-musl.sh`, which also runs `oxabl self-update --check` against a closed loopback port and wants exit 3). The CI job `Self-update` runs `cargo test -p oxabl --features self-update --test self_update`, and the job `Install script` runs `scripts/install.sh` under shellcheck, dash and bash against a fake release server (`crates/oxabl/tests/install_script.rs`). The `check` job fails when a default `oxabl` or `oxabl_build` build names a `reqwest`, `rustls` or `tokio` crate.

## Benchmarks

Benchmarks use `codspeed-criterion-compat` (Criterion with CodSpeed integration). CodSpeed CI runs on every push/PR via `.github/workflows/codspeed.yml` and auto-discovers all `[[bench]]` targets.

```bash
# Run benchmarks for a specific crate
cargo bench -p oxabl_lexer --bench lexer_bench
cargo bench -p oxabl_parser --bench parser_bench
cargo bench -p oxabl_common --bench source_map_bench
```

**When the `/codspeed` skills are available, use them for benchmark work** — setup, optimization, and flamegraph analysis.

**When implementing new features**, consider whether a new benchmark is warranted. If the feature adds a new parsing construct, expression type, or hot path, add a benchmark to cover it. This ensures CodSpeed catches regressions as the codebase grows.

The end-to-end and memory benches are in `crates/oxabl_bench` (not published; `e2e_bench`: `check/file`, `check/workspace`, `check/workspace_include_findings`, `check/include_findings_repeated`, `format/file_end_to_end`, `navigation/definitions`, `navigation/links`; `large_bench`: `lexer/large_mixed/*`, `parser/large_mixed/*`, `semantic/large/*`) and in `crates/oxabl_daemon/benches/daemon_features_bench.rs` (`daemon_cycle/features_on_one_revision`, `workspace_symbols/query`). They install the counting allocator `oxabl_bench::alloc::Counting` and print the allocations, bytes, peak and retained bytes of one warm iteration (`OXABL_BENCH_MEMORY=<file>` appends them as JSON lines). `crates/oxabl_bench/tests/alloc_budget.rs` holds the allocation budgets of the lex and the parse of `resources/lsp_bench.p`, and of the parse of `crates/oxabl_schema/fixtures/sp2k.df` (a parser of `.df` text that makes a string for a keyword fails it; both run in one test, because the counter is global): the band is 0.5% on both sides, so a pull request that lowers a number lowers its budget. `tests/include_rows_alloc.rs` fails when a finding in an include costs more than 9 allocations in the lint run when it makes a row, or more than 7 when it joins the row of an earlier expansion (the fold of `IncludeRows` in `oxabl_analyze` must not clone a path or a message; the test counts allocations only, so a slower hash shows in callgrind and in the benches `check/workspace_include_findings` and `check/include_findings_repeated`). `tests/fixtures_parse.rs` fails when a bench input has a parse error. `tests/generate.rs` keeps every generated root free of findings and drift, counts the findings of `--include-findings`, pins the `ci` workspace by a fingerprint (the CodSpeed benches compare by name, so a change of the generator must not change one byte of it, or must update the fingerprint on purpose), and keeps the `erp` preset inside a band around the counts that a scan measured on a large real workspace (`docs/performance.md`, "The `erp` preset"). `scripts/bench/gen-workspace` writes a deterministic synthetic workspace (presets `ci`, `medium`, `erp`), and `scripts/bench/cli.sh` measures the release binary with GNU `time`, heaptrack (a binary built with `RUSTFLAGS="--cfg oxabl_system_allocator"`, a flag and not a feature so that nothing can turn jemalloc off in a release) and callgrind. The CodSpeed job `codspeed-memory` runs the lexer, parser, `oxabl_bench` and `oxabl_daemon` benches with the Memory instrument. `docs/performance.md` is the guide.

- Read every file of a bench from an `InMemoryFileSystem`: the Simulation instrument does not count system calls.
- Put new forms in a **new fixture with its own bench** (as `compiler_forms` and `type_spellings` do), not in an existing fixture. CodSpeed compares a bench by name, so a grown fixture reads as a regression, and it hides a real cost of the change in the old input.
- Measure the existing benches against the base **before** you add a fixture, with the same input on both sides. When the machine is loaded, count instructions instead of wall time: `valgrind --tool=callgrind --toggle-collect='*parse_program*' oxabl conformance -j 1 <file>` on a base and a candidate release binary.

## ASD-STE100 Simplified Technical English

Always respond using ASD-STE100 Simplified Technical English. It is a controlled writing standard. Aerospace and defense groups made it. It helps people write clear technical text.

Key rules:
- **Use approved words only.** The standard gives a word list. Each word has one meaning.
- **Use one word for one idea.** Do not use two words for the same thing.
- **Write short sentences.** Use 20 words or less for instructions.
- **Use active voice.** Write "Turn the switch", not "The switch must be turned".
- **Write short paragraphs.** Keep one topic in each paragraph.

The goal is easy reading. Many readers are not native English speakers. Clear text helps them do the work in a safe and correct way.
