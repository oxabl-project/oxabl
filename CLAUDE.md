## Project Overview

Oxabl is a high-performance tooling suite for Progress ABL (Advanced Business Language), written in Rust. The project aims to provide blazingly fast developer tools for ABL code (formatting, linting, parsing, etc.). This is an unofficial project with no affiliation with Progress Software.

## Code Generation

The lexer uses generated code for ABL keywords, operators, and the keyword matching function. The `oxabl_codegen` crate parses reference HTML/JSON files from `resources/` and generates Rust code.

```bash
# Write all generated files (default)
cargo run -p oxabl_codegen

# Write specific file(s)
cargo run -p oxabl_codegen -- kind     # Writes kind.rs (enum + match function)
cargo run -p oxabl_codegen -- atoms    # Writes build.rs (complete file)
cargo run -p oxabl_codegen -- callable # Writes callable.rs (is_callable_kind)
cargo run -p oxabl_codegen -- builtins # Writes builtins.rs (built-in function registry)

# Show statistics without writing files
cargo run -p oxabl_codegen -- summary
```

Generated files are written directly to their target locations and include a "DO NOT EDIT" header.

### The OpenEdge metaschema catalog

`crates/oxabl_schema/resources/metaschema.df` is a generated `.df` describing
the dictionary and virtual system tables that every OpenEdge database carries
(`_file`, `_field`, `_index`, `_connect`, ...). A `.df` dump never contains
them, so no project can supply them. It is parsed once per process and
*borrowed* by every loaded schema — never copied — and the user's own tables
always win a name collision.

It is generated by shell rather than `oxabl_codegen`, because it can only be
produced from a licensed OpenEdge installation:

```bash
DLC=/path/to/dlc scripts/gen-metaschema-df.sh
```

See `crates/oxabl_schema/METASCHEMA.md`.

## Architecture

### Workspace Structure

- `crates/oxabl` - Umbrella library (the curated public API) and the CLI binary
- `crates/oxabl_pipeline` - The shared lint and format run every client drives; sits *beneath* `oxabl_lsp`, `oxabl_wasm`, and the umbrella
- `crates/oxabl_index` - Cross-file fact extraction, the in-run batch index and the static call graph; sits *beneath* `oxabl_pipeline`
- `crates/oxabl_daemon` - The session core: one salsa instance per workspace root, serving several clients; the **only** crate that may know about salsa
- `crates/oxabl_daemon_protocol` - Wire types and the contract version for the daemon's `oxabl/*` methods; depends on serde and nothing else
- `crates/oxabl_lexer` - Tokenizer for ABL source code (MVP complete)
- `crates/oxabl_ast` - AST node definitions (expressions, statements, literals)
- `crates/oxabl_parser` - Parser for ABL source code (actively developed)
- `crates/oxabl_common` - Shared utilities including `SourceMap` and the `catch_panic` guard
- `crates/oxabl_codegen` - Code generation tool for lexer keywords
- `crates/oxabl_flow` - Control-flow graphs per unit with ABL block semantics, plus a dataflow solver
- `crates/oxabl_handles` - Lifetimes of dynamic objects per unit (create, free and escape sites, leaking paths), read by the `strict.handles` rules
- `crates/oxabl_scope` - Buffer scopes, transaction blocks and lock modes per unit, as the compiler assigns them, plus the `COMPILE ... LISTING` block-table parser its oracle harness uses
- `crates/oxabl_effects` - Database effects per unit (table, operation, lock, access shape, likely index), transitive summaries over the call graph, the `COMPILE ... XREF` parser its oracle harness uses, and the reader of the files that `XREF-XML` says the compiler opened
- `crates/oxabl_build` - The `oxabl build` tool: the SQLite graph store with its generations and crash recovery, the incremental refresh that hashes before it parses and keeps an observation set per analysed file, the in-memory graph, the planner that says which units must rebuild and why (`oxabl build --plan`), and the AVM worker pool with the `OXW1` worker protocol (the worker program is `resources/oxabl_worker.p`, embedded), the configuration (`config`: `oxabl.toml` with the `--config-overlay` file merged over it key by key, the rules that refuse a key an overlay may not set, a secret-looking key and a trust key of the remote cache, and the effective settings with their sources for `--print-config`), the compile environment and its identity (`oxabl build --probe`), and the compile key of each unit with the fail-closed rules that withhold it (`oxabl build --plan --probe`), the scheduler (jobs over the strongly connected components of the compile-time graph, priority by critical path), output ownership, staging and promotion, the stored compile results and the results-based plan reasons, `oxabl build` itself (`run`: the fetch of keyable units, dispatch, retry, lost workers, cancel, `--events`, `--report`), the cache seam (`cache`: `ArtifactCache` with a streaming fetch and uploader, the local cache with quarantine and eviction, the chain of two caches, the mode and trust rules, the per-job directory) and the verification of what a cache may store (`verify`: V1 rehash, V2 schema check, V3 read check; the `XREF-XML` reader is `oxabl_effects::xref_xml`). Sits above `oxabl_pipeline`; the umbrella re-exports it as `oxabl::build` under `cli`
- `crates/oxabl_build_remote` - `RemoteCache`, the `ArtifactCache` over the oxabl-cache client, behind the umbrella feature `remote-cache`. The client is a git dependency pinned to one revision in the root `Cargo.toml`, in `[workspace.dependencies]`: a crates.io version replaces that line once the client is published. Only this crate links it; CI fails when `cargo tree -p oxabl_build` or a default `oxabl` build names an oxabl-cache crate. Its black-box tests are `crates/oxabl/tests/build_remote_*.rs` and run against the real server, admin and member binaries (`scripts/remote-cache-binaries.sh <dir>` builds them at the pinned revision; `OXABL_CACHE_SERVER_BIN`, `OXABL_CACHE_ADMIN_BIN` and `OXABL_CACHE_BIN` name them; a missing binary fails the tests): `cargo test -p oxabl --features remote-cache --test build_remote_cache --test build_remote_faults --test build_remote_trust`
- `crates/oxabl_fake_avm` - A fake AVM that speaks the worker protocol, including compile requests and the faults the build tests need, for black-box tests of `oxabl build`. Not published. It has no oxabl dependency, on purpose: CI fails when `cargo tree -p oxabl_fake_avm` names an oxabl crate
- Real-AVM suite - `crates/oxabl/tests/build_openedge.rs` and `build_openedge_scratch.rs` (with `build_openedge/`, `common/openedge/` and `fixtures/openedge/`): the opt-in tests of `oxabl build` against OpenEdge. Every test is `#[ignore]` and fails, never skips, without its `OXABL_OPENEDGE_*` variables; the variables and the commands are in `docs/overview.md`, "Testing against a real AVM". CI builds them and runs none
- `crates/oxabl_nulls` - Unknown values per unit: buffers a failed `FIND ... NO-ERROR` may leave without a record and the field references that read them, and local variables that may hold `?` with the uses they reach

(Not exhaustive — the workspace also holds `oxabl_preprocessor`, `oxabl_semantic`, `oxabl_schema`, `oxabl_lint`, `oxabl_analyze`, `oxabl_formatter`, `oxabl_style`, `oxabl_workspace`, `oxabl_lsp`, and `oxabl_wasm`; see the status section below.)

### Lexer (`oxabl_lexer`)

The lexer should classify tokens as distinctly as possible so the parser dispatches on `Kind` enum variants (O(1) integer comparison), never on runtime string comparison or `to_uppercase()` allocations. When a new keyword is needed by the parser, add it to `keyword_overrides.toml` and regenerate — do not use `eq_ignore_ascii_case()` workarounds.

**Avoid heap allocations on hot paths.** ABL keywords are ASCII-only, so case-insensitive matching uses a `[u8; 64]` stack buffer with `to_ascii_lowercase()` byte folding — never `s.to_lowercase()` which heap-allocates a `String`. Eliminating the `to_lowercase()` allocation in `match_keyword()` (called on every token) yielded a ~20% overall performance improvement. The codegen emits a compile-time assertion that the longest keyword fits in the buffer. The same principle applies anywhere in the lexer: prefer `eq_ignore_ascii_case()` (zero-allocation byte comparison) over `to_lowercase()` + match.

The lexer tokenizes ABL source code into a stream of tokens. Key components:

- **Token**: Contains `kind` (token type), `start`/`end` byte offsets, and `value` (for literals)
- **Kind**: Enum of all token types (operators, keywords, identifiers, literals)
- **TokenValue**: Enum for literal values (Integer, BigInt, Decimal, String, Boolean, None)

The lexer uses `string_cache` for interned strings (atoms). Atoms are generated at build time via `build.rs` which includes all ABL keywords.

ABL-specific features handled:
- Case-insensitive keywords with abbreviations (e.g., `def`, `defi`, `define` all map to `Kind::Define`)
- Tilde (`~`) as escape character in strings
- Hyphens allowed in identifiers (`my-variable-name`)
- Preprocessor directives (`&if`, `&scoped-define`) and references (`{&variable}`)
- Include file references (`{file.i}`, `{file.i args}`, `{file.i &name=value}`)
- Include positional argument references (`{0}`, `{1}`, `{2}`)
- Line (`//`) and block (`/* */`) comments

### Code Generation (`oxabl_codegen`)

Parses ABL keyword reference data from:
- `resources/abl_keyword_index.html` - Keyword list with reserved status and abbreviations
- `resources/abl_keyword_index.json` - Keyword types and documentation URLs
- `resources/keyword_overrides.toml` - Manual additions, overrides, and removals

Generates:
- `Kind` enum with categorized token types
- Atom list for `string_cache_codegen`
- `match_keyword()` function handling abbreviations and case-insensitive matching

## Benchmarks

Benchmarks use `codspeed-criterion-compat` (Criterion with CodSpeed integration). CodSpeed CI runs on every push/PR via `.github/workflows/codspeed.yml` and auto-discovers all `[[bench]]` targets.

```bash
# Run benchmarks for a specific crate
cargo bench -p oxabl_lexer --bench lexer_bench
cargo bench -p oxabl_parser --bench parser_bench
cargo bench -p oxabl_common --bench source_map_bench
```

**When the `/codspeed` skills are available, use them for benchmark work** — setup, optimization, and flamegraph analysis.

**When implementing new features**, consider whether a new benchmark is warranted. If the feature adds a new parsing construct, expression type, or hot path, add a benchmark or extend an existing fixture file to cover it. This ensures CodSpeed catches regressions as the codebase grows.

## ASD-STE100 Simplified Technical English

Always respond using ASD-STE100 Simplified Technical English. It is a controlled writing standard. Aerospace and defense groups made it. It helps people write clear technical text.

Key rules:
- **Use approved words only.** The standard gives a word list. Each word has one meaning.
- **Use one word for one idea.** Do not use two words for the same thing.
- **Write short sentences.** Use 20 words or less for instructions.
- **Use active voice.** Write "Turn the switch", not "The switch must be turned".
- **Write short paragraphs.** Keep one topic in each paragraph.

The goal is easy reading. Many readers are not native English speakers. Clear text helps them do the work in a safe and correct way.
